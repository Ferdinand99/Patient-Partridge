# Known limits

This page lists what Patient Partridge does not do yet, and where its edges are. The [README](../README.md) names the main ones; here they are in full. What the app does is in [features.md](features.md); how it is protected is in [security.md](security.md).

Making forms, pictures of signatures and the page tools are new in 0.3.0 and are not in a released version yet. Editing text and images, redaction, certificate signatures and the other steps on the roadmap are planned and do not exist yet; see the [Roadmap](../README.md#roadmap).

## Annotations

- *Colour.* The engine draws a note the same way whatever its colour (PDFium has one picture for it), so a note has no colour to choose. The colour of a highlight, an underline or a strike-out can be changed in place: the picture of the annotation is made again and the colour entry is set, and every other entry of the annotation (rich text, name, dates, opacity, layer, popup, replies) stays as the file had it; the opacity is kept to within 1/255. Changing the colour replaces the picture with a plain one in the new colour, and Undo makes a plain picture in the old colour, not the file's own picture. The old colour is read from the first path of the picture that paints something (the fill of a highlight and the stroke of the others when they are painted, otherwise the other one), also when the picture draws through forms inside forms; a picture with no path to read it from is not recoloured (the bar says so).
- *Text.* The text of a file's annotation is edited only when it is shown whole: a comment longer than 4 KiB, or with characters the window does not show, can be read but not edited here. Line ends written as CR are shown as line feeds and written back as they were when a change of the text is taken back. Editing the text of an annotation that has rich text (`/RC`) replaces the rich text with the plain text, so its formatting is lost; taking the edit back (Undo) writes the comment, the rich text and the date of the last change as the file had them.
- *Undo and delete.* An annotation that a file already has cannot be put back by Undo after it is removed (a copy would lose what the engine does not read), so deleting one asks first; one made in this session can be put back. Deleting one from a file is not an entry in the history: it clears Redo, Undo still takes back the changes made before it, and the document counts as changed until it is saved. Of those, taking back a delete, a move or added pages loads the document as it was then, with the annotation in it; taking back a turn or a crop does not. Edits that were made to that same annotation before it was deleted do nothing when they are undone or done again, and Undo goes on to the edits below them.
- *What a delete leaves in the file.* Deleting an annotation and saving rewrites the whole file, and the text of the comment, its author, its rich text and its subject are not in the new file; its popup goes with it. If a reply or the document's tag structure refers to the annotation, an empty record of it stays, with its place on the page and its dates. **This is not redaction:** nothing on the page itself is removed, and copies and backups made before the save still hold the text. PDFium does not write the objects of a loaded file that nothing refers to any more (also when they sit in object streams), but it does write those made in the session, whether or not anything still refers to them: the picture of a signature that Undo took off, a drawing or a stamp that was deleted, the appearance of a note. So a save writes the document, reads what it wrote in again as a document of its own and writes that a second time; the second writing is the file, and it holds nothing that was made in the session and then taken off. This also covers a free text box that came without an appearance stream: PDFium makes the appearance, with the words in it, when the page is first drawn, and the second writing leaves it out once the box is deleted. The text of an annotation is still overwritten when it is removed or changed. The second writing costs one more load and one more write of the same bytes (about 60 to 70 % more time than the first writing alone on a document of 20,000 pages), and the memory for the second copy: when there is not enough memory to finish the second writing, the save stops and says so (nothing is written), also for a file well under 512 MiB.
- *Boxes and moves.* A note cannot be moved off its page. A box a file puts outside its page is cut to the page in the window; a note a file puts partly outside its page can be moved in and then moved back to where it was, and not further out.
- *Kinds.* A drawing is written with a list of strokes and an appearance stream; PDFium cannot move or change the strokes of an existing drawing, so a drawing cannot be edited here, only removed. Free text boxes, squares, circles and squiggly underlines of a file are shown and can be removed, not changed. Link and form-field annotations are not listed. A stamp is a drawn frame and word in a standard font, not an image; its wording is fixed.
- *Permissions and signatures.* A document opened with its owner password may be annotated whatever the file grants the user. A document with a digital signature gets the warning described under [Saving and digital signatures](#saving-and-digital-signatures), because saving rewrites the file.
- *Other readers.* Whether commercial PDF readers let a person edit a drawing's strokes was not tried; `qpdf` and Poppler read the files without complaint.

## Memory

Measured on Linux (WebKitGTK, software rendering) with a 500-page file open: the whole app, all its processes together, uses about 490 MB of memory (proportional share), of which about 325 MB is the web view and about 14 MB the engine. The goal of 150 MB is not met there. Windows and macOS have not been measured on real hardware; their web views behave differently.

## Web view

The look uses CSS `light-dark()`, so the web view must be recent: WebView2 (always up to date), WebKitGTK 2.46 or newer, and a macOS version whose web view is Safari 17.5 or newer.

## Search

Search finds text as PDFium reports it. It does not join words split by a hyphen at the end of a line, and it does not match a ligature character against its letters. A search stops after 20,000 matches and says so (for example "20,000+ (stopped at the limit)"); a page with more than 2,000 matches shows the first 2,000 and the find bar says that some pages have more.

## Text selection

Text selection follows the order of the text in the file. In documents with several columns that are stored in an odd order, a selection can jump between columns. Right-to-left text (Hebrew, Arabic) is selected from its right end, in reading order; text that runs sideways or up and down is not placed well yet.

The keyboard cannot select a stretch of text yet (Ctrl+A selects everything), and the pen needs a pointer: there is no way to draw with the keyboard.

## Text layer

For each document the window keeps the text of at most 1.5 million characters (about 60 MB) for the pages on screen, and the addresses of their links up to 1 million characters. A page that would go past that is drawn as usual but has no text layer for the moment: its text cannot be selected, searched on the page or pressed as a link, and a message says so once. The window also draws at most 20,000 boxes for the selection and the search matches together, and 5,000 link buttons, for a document, and keeps at most 120 pages on screen at once. A page that does not get all its boxes or buttons is drawn as usual and a message says so once; copying and searching are not affected. Normal reading does not reach these numbers. A very small zoom on a large screen can, with a search for a common letter or with index pages that hold hundreds of links each. The text limit itself is reached only by files made to do it, such as thousands of tiny pages that each hold the most text a page can have.

## Copying

Copying gathers at most 20 million characters at a time, one copy at a time for each document. When a copy is cut short, or a page cannot be read, or a page has more text than the engine hands over (100,000 characters), a message says what is missing. On some systems the web view allows the text to be put on the clipboard only straight after a key press; if it refuses, a message says so.

## Printing

Printing sends pictures of the pages, at 150 dpi, to the system's print dialog. Pages of different sizes are fitted to the paper. One print job holds at most 1,000 pages: for a longer document the dialog offers "The first 1000 of N pages" instead of "All", and a list of pages can be printed in parts. Printing has not been tried on a real printer on any system yet (see [features.md](features.md#printing)).

## Fonts that a PDF does not embed

The engine runs in a sandbox that does not let it open files, so it cannot look at the fonts installed on your system. For Latin text it uses the fonts built into PDFium (Helvetica, Times, Courier and anything named like them). For Chinese, Japanese, Korean, Arabic, Hebrew and Thai the app picks one font file for each script from a fixed list of the files that Windows, macOS and the usual Linux font packages install (the PDF never chooses a file), opens each read-only, and hands the engine those handles; the engine reads a font only when a page needs that script, checks it, and hands PDFium at most 512 MiB of font data for a document. [system-fonts.md](system-fonts.md) lists the files per system. Only those file names in the system's own font folders count: a font that is installed for one user only, or has another file name, does not, even if it covers the script. The list is read again each time a document is opened, so a font you install for all users is used from the next document you open (close the tab and open the file again: a tab that is already open keeps what it had); a file that is missing, cut short or not a font is passed over for the next one in the list. CI draws a page in each of the seven scripts with what the images of the GitHub runners have (Windows and macOS as they come, Ubuntu with the Noto and DejaVu font packages), and also as a standard Windows user. A collection file (.ttc) is used from its first face, and one file can serve several scripts (on macOS the same Chinese font serves Simplified and Traditional, on Windows Segoe UI serves Arabic and Hebrew). Chinese, Japanese and Korean are drawn from the character set the PDF asks for, whatever the font is called, also when the name is written in the code page of the language (GBK, Shift-JIS, EUC-KR, Big5). Arabic, Hebrew and Thai are drawn only when the PDF names a font made for that script (such as Traditional Arabic, David or Angsana), because PDFium asks for those by name alone: text in them that a PDF sets in Arial, Tahoma or Times New Roman without embedding the font shows as blanks, and the window does not know that it does. When the PDF needs a font for a script, the computer has none of the listed ones (or the document asks for more copies of fonts than the 512 MiB allow: PDFium keeps one copy for each combination of font name, weight and slant, and font objects that ask alike share it), that text shows as blanks and the window says so once for the document; you can still search, select and copy it. Almost every PDF made for print or the web embeds its fonts and is not affected. Fonts put in a `fonts` folder next to the PDFium library are read at start and used too; the app does not ship any.

## Forms

XFA forms (the kind drawn from XML data, whole or next to ordinary fields) are shown but not filled in: a reader that supports XFA would show the XFA data and ignore ordinary fields, so a value written to them would not appear. The app says so in a bar over the pages. PDF JavaScript never runs, so a form that adds up, checks or formats values by script opens and can be filled in, but those fields do not update; the app says so once, in the same bar, when it finds a script or an action on a field (it looks at the scripts of the document, the words of the file, and the actions on the fields of the pages it shows, so a script hidden in a compressed part of a document it does not otherwise meet can go unnoticed).

**Actions that change a form are checked before you can fill it in, and the check has a limit.** PDFium runs the actions of a field that are not scripts by itself when the field gets the focus, is pressed or is left, and two of them change the document: a reset of the form and a hide of fields. So the app reads the actions of a form before it lets you fill it in: the engine writes the document out once and, if it holds a reset or a hide, reads what the actions of every dictionary do: it follows `/A` and `/AA`, through references and `/Next` (one action or an array of them), to see whether a chain reaches a reset or a hide. A field is left read only and marked in two cases. If its own actions reach one, that field is left alone, and nothing else is: a reset button, a script that formats a date or a number, or a link next to it do not stop other fields. If the keystroke, validate, format or calculate event of any dictionary reaches one, every field of the form is left alone, because PDFium reads those events from a field other than the widget (it looks up `/Parent`, builds a field from the list of its kids, and joins two dictionaries with one full name by that name alone), and the file does not say which widget belongs to which. Every field is also left alone when the search cannot settle: an action that points to nothing, a loop, a chain or nesting that is too long, more work than the limits allow, a file that failed to read or changed while it was searched, or a compressed object stream, whose content is not read. A widget with an action is matched with the dictionaries of the file by which of `/A` and `/AA` it has and by its box, not by its page or its place in a list; it is left alone when a dictionary with that box and those keys reaches a reset or a hide, and also when no dictionary matches, so a harmless widget with the box of a harmful one is left alone too. A dictionary with no `/Rect` at all (a page, the document, a bookmark, a field above its widgets) is not a widget and blocks no field, because PDFium never runs its actions from here. The bar says in plain words which of the two it is, says it again when the reader tries such a field, and a request to change it is refused.

**This is a reading of the file, not a guarantee:** a file built to get round it could still clear or hide a field in the open document. Nothing leaves the app, and the file on disk changes only if you save. Scripts never run, so a script that does not reach a reset or a hide through `/Next` blocks nothing. The other actions (a link, a jump, a launch, a submit, a named action) end in something the engine does not provide, so they do nothing. A push button over a field is never pressed: the field that is named gets the key, not whatever lies at its place. Push buttons and signature fields are not listed.

**Two kinds of choice cannot be taken back:** PDFium has no way to turn a radio button off, or to clear a drop-down list, once a choice is made, so the undo of the first choice in such a field is refused with a message (a different choice can be made, and undone). A field whose value is longer than 8 KiB, or a list with more than 500 choices, is shown and left alone. The Tab order is the order of the fields on the page (the order of the file); the page setting that asks for another order is not used. A field that is itself turned in its own right (the entry `/MK /R`), and not only by the page, is drawn turned by PDFium but its control is not. Text that a field's font cannot draw (a script the fonts of the engine do not cover) is stored correctly but the picture of the field may show blanks, until a reader that has such a font redraws it.

Which readers were tried: poppler, qpdf and pdftk read the saved test files in CI; commercial PDF readers have not been tried by the project.

## Making forms

The document must be one the writer can read: an encrypted document, an XFA form and a document whose structure the writer does not understand are refused with the reason, and nothing is changed. Text a field draws (a starting text, a choice) can use the characters of Latin-1, which include æ, ø and å; a character outside it (a euro sign, Cyrillic, Greek, Chinese) is refused with a message that names it, because the standard font would draw a blank. Names and tooltips are not drawn and may hold any character. The designer changes only fields that sit at the top of the form's list, with a name without a dot, of a kind it makes, with no action; every other field is shown with a dashed outline and left alone. A page can have 1,000 fields, a radio group 64 buttons, a list 500 choices. A signed document is rewritten by a save like for any change, so the usual warning comes first, and the verdict on its signature is dropped as soon as the form is changed. A place to sign that nobody has signed does not make a document count as signed. On a page that is turned the field is written turned with the page, so its text reads upright; other readers draw it that way in the tests (Poppler, PDFium), and readers that were not tried may differ. The fonts are Helvetica and ZapfDingbats from the standard set; no font is embedded. A form that already has scripts keeps them, and a field made here in such a form is blocked from filling in when the form is blocked as a whole (see Forms below). Opening a created file in the reader you will send it to before you rely on it is a good idea: only the tools named above, PDFium and Poppler, were tried.

## A picture of a signature

- *What it is.* A stamp annotation with an appearance made of lines, curves or an image, and the print flag. Another program that edits annotations can move, change or delete it, and one that hides annotations hides it. It proves nothing about who placed it.
- *After a save.* Once the file is saved and opened again, a picture is an ordinary stamp: it can be removed, but not moved or resized. Moving and resizing work on the pictures placed in the session, with the same Undo as the other changes. A page of a signed document is edited like any other, and the check of the digital signatures drops its result (see below).
- *Limits.* A drawing has at most 64 lines and 4,096 points; a typed name at most 40 characters, and only letters the font has (the Latin scripts: other letters are refused with a message); an imported image is scaled down to at most 1,024 by 1,024 pixels and 524,288 pixels in all, and a PNG, JPEG, WebP, GIF or BMP file that declares more than 8,192 pixels on a side or 16 million pixels is refused from its header before anything decodes it (for a GIF the largest of the screen and of every frame counts, the whole file is walked to find them, and a GIF that is cut short, has no frame, or has an extension that is not in the form the format gives is refused, because some decoders read such an extension differently and would find another frame; for a JPEG the segments up to the scan are read by their lengths, a 0xFF 0x00 or a stray byte where a marker should be is refused, and everything after the start of the scan (the data and what follows the end of the picture) is searched for every start of frame, the largest counting, so that no decoder finds a size the check did not see (a file with something after its end that looks like a start of frame, or that is cut short there, is refused); an animated GIF gives its first picture); at most 20 pictures are kept on the computer, each image at most about 400 KB as a PNG. The engine keeps the pictures of a document in memory to put them back after an Undo, at most 32 MiB of them. PDFium keeps what it made for a picture until the document is closed, even after the picture is taken off, so putting pictures on and off and back again is also held to 256 MiB in all for an open document, whatever is done to its pages meanwhile; past that the box says to save the document and open it again. SVG and other drawing files are not read as images.
- *Fonts.* The three script fonts (Great Vibes, Allura and Kristi, all under the SIL Open Font License 1.1) are shipped as subsets, and their licences are in THIRD-PARTY-NOTICES. The window shows the typed name without kerning or ligatures, as the engine sets it, but the width of the preview is measured with the browser's own text engine, so the box can differ a little from the picture on the page.
- *Other readers.* `qpdf` reads the files, Poppler draws the pictures where the engine put them and prints them (checked in CI). Commercial PDF readers were not tried.

## Page tools

All of it is tested against the bytes of the saved file with the real PDFium, in the sandbox, and (on Linux, in CI) read back by qpdf and poppler.

- *Delete* removes the page from the file, with its text, pictures, fonts, notes and everything else that only that page used (PDFium writes only what can still be reached from the document, apart from objects made in the same session, so the words of the notes and other annotations on a page are overwritten before it is deleted; the tests search the saved bytes for the text, the picture, the note, the font name and the form value of a deleted page). Bookmarks that led to it stay in the list and lead nowhere. **A delete is not redaction, and some things stay.** PDFium keeps the list of the form's fields, so a field that sat on a deleted page stays in the file with its name. Before the page is deleted the app clears the text typed into text fields, their default values and tooltips, and the picture of the typed text (the appearance of the field), and the window says that form fields were on the pages; other kinds of fields (check boxes, choices) and fields grouped under a parent field may keep what they hold, and so do the lists of choices of choice fields, the captions of buttons and the text of a note that a tag points at. In a tagged document the alternative text and the actual text of the tags of a deleted page stay in the file, because PDFium gives no way to remove them; a test pins this, so a change is noticed. A form field whose widget a page that stays also lists (one annotation named by two pages) is left as it is, with its value and its look, because that page still shows it. The window says all this the first time a page is deleted from a document. Do not rely on a delete to remove confidential content; real redaction is planned.
- *Move* (drag, or Alt with an arrow) uses PDFium's own move of pages, which changes the order in the page tree and copies nothing. Links to and from a moved page, its bookmark, its form fields and its tags stay as they were. The pages that can stay in their order are not touched. A page can inherit its resources (fonts and pictures), its size, its crop box and its turn from a node of the page tree above it, and PDFium's move puts a page under another node without them. When a node below the root of the tree holds such an entry, the engine first writes what each page inherits onto the page itself (a part added to the end of the document as PDFium wrote it, which is then read in again; a value that is written in place and is long is written once, as an object of its own, and the pages refer to it, and the part is refused, with the document left as it was, when it would add more than the size of the document and four megabytes), and goes on only when every page looks as it did before: the same size, turn, boxes, number of drawn objects and fonts. After the move the same look is compared again, and a move that changed a page is refused and taken back. The tests draw every page of documents that have such entries at three levels of the tree before and after several moves, through the engine and through the saved file, and compare the pixels; in CI poppler draws the saved file and the original the same way.
- *Adding pages from other files and copying pages out* carry the pages with what they show, their notes and their links to pages that come before them in the same copy. They do not carry bookmarks (outlines), links to pages that come later or are not copied, the structure of tagged documents, the information of the document (title, author), form fields (they stay on the page as they look but cannot be filled in; a field name that two files share therefore causes no clash) and signatures. This is how PDFium copies pages. PDFium also leaves the `/Parent` entry of a copied annotation as it was in the other file, where it named the note of a pop-up or the field of a form widget; in the new file that number means some other object, which is wrong although the file is valid (qpdf finds nothing). A pop-up and a form field shown on several pages therefore lose the link to their note or field. A test pins this, so that a PDFium that repairs it is noticed. A page that comes keeps the size, the crop and the turn it had in its own file: if the node it lands in would give it others, they are written onto the page. The window says what does not come along after the first pages are added to a document.
- *Passwords.* A file whose pages are added asks for its password; its pages then join this document **without that protection** and the window asks first (if this document has a password, the pages are protected by it when it is saved). A copy of pages out of a protected document has **no password**, and the window asks first. A document with a password keeps it through every tool: the engine holds the password in memory while the document is open, to load copies of the document, and overwrites it with zeros when the document is closed (it is not protected against a dump of the engine's memory). Nothing ever tries a password.
- *Signatures.* The page tools do not make a signed document worse than a save does: saving it warns, because a save writes the whole file again and breaks the signature (see above). The pages of a signed file come without the signature, and so do pages copied out of a signed document; the window asks first. The signature field stays on the page as it looks, and the data of the signature (the byte ranges and the signer's certificate) is not copied: a file made that way is not counted as maybe signed when it is opened.
- *Crop* sets the crop box of the page, the part of the page that readers show. **It does not remove anything**: the text, pictures and everything else outside the box are still in the file, and a program that ignores the crop box shows them. The box for cropping says so. The part that is shown is the one the page is drawn with, also when the media box or the crop box comes from a node of the page tree above the page, and a new blank page has exactly the size asked for whatever such a node says. Deleting the page takes its content out of the file, with the exceptions listed under Delete; real redaction is planned.
- *Limits.* The page tools work on documents of up to 10,000 pages and on up to 10,000 pages at a time; the reader opens documents of up to 100,000 pages and refuses more (a file can claim millions of pages in a few bytes). A file that is added is read by an engine of its own, at most 512 MiB, and the document and the file together may have at most 10,000 pages. A blank page has sides of 8 to 14,400 points. A crop must leave at least 8 points. Before pages are deleted, moved or added (a blank page, the pages of another file) the engine reads the page tree of the document as PDFium writes it, with a reader of PDF objects (not a search for words), and refuses the change when the tree does not follow the format: a place in a list of kids that holds something that is not a page or a node (PDFium stops the process on a null entry, which the fuzz target found), a node that says it has another number of pages than it lists, a tree that loops, or (for a move, and only when a node of the tree holds an entry that its pages inherit) a page that does not name the node that lists it, or a page that names a parent that no list of kids lists (or a chain of such parents) when that parent holds an entry that its pages inherit; PDFium finds what a page inherits by following its parent, and a move would take it away. A parent outside the tree that holds nothing is no obstacle. A tree is read with limits: a page that a list names many times is read once, only what the reading needs is kept, and a reading that takes more work than a few times the size of the document is given up as "could not be checked". An entry that leads to nothing (a reference to an object that is not there, or `null`) counts as no entry, which is what the format says. A list of kids that is an object of its own, the words `stream` and `endobj` inside strings, object numbers above a million and files written with object streams are all as valid as they are, and are changed as usual. A tree that the reader cannot follow is refused too, with words that do not blame the document ("could not be checked"). A turn, a crop and copying pages out do not go through the tree and work on such a document as before. Deleting, moving and copying take time in proportion to the number of pages; a move of every page of a very long document can take minutes. A change to the pages can still crash PDFium on a file that is damaged in the right way; that ends the engine of that document like any other damaged file: the tab closes with the usual message, the changes that were not saved are lost, and the file on the disk is untouched. Pages that are copied in (an insert) point into the other file until the document is written out and read in again, so the document goes through exactly that before the other file is let go of, and the result must have the pages it should or the change is taken back. A change that fails half way is undone from the copy of the document, and when that is not possible the document is closed rather than left half changed, so what is saved is never half of a change. A file of no pages is never written: the save refuses a document that describes itself as having none.
- *With annotations and forms.* While a page tool (or taking one back) works on a document, its annotation tools, the box for the text of a note and the fields of its form wait and say why: a change begun then would run after the pages changed, with page numbers that mean other pages. Before a tool begins, text typed in a field and not left yet is sent, the open box of a note is saved and the changes under way are made, so that they are part of the document first; text that a field refused (too long for the document) is not in the document, and the tool does not begin until it is dealt with. When the pages have changed, the layers of the fields and of the annotations are made again for the new list, nothing stays picked, and the engine drops the environment of the form, which it makes again from the document. The engine keeps what it knows of the annotations (their numbers, and what can be put back after a removal) with each copy of the document that takes a change back, so the numbers of that state come back with it. A field that has widgets on a page that stays keeps what it holds when another page is deleted.
- *Taking a change back.* For a delete, a move and added pages, the engine keeps copies of the document as it was, in memory: at most 32, and at most 256 MiB together, the oldest first to go. A change that needs a copy of a document too big to keep one is made, and the window says that it cannot be taken back. A turn and a crop need no copy. Taking a change back loads the copy and keeps the state it leaves, so it can be made again; each copy records the number of pages it must show, and a copy that reads back with another number is refused instead of replacing the document. A document of more than half of the 256 MiB can still be taken back and made again once; it keeps fewer older steps. The history of the window holds 200 changes.
- *Stop.* Pages that are being added or copied out travel between engines in pieces of at most 1 MiB, and Stop ends that at the next piece: the document is as it was. When the engine is in the middle of a change to the document itself (a delete, a move, a turn, a crop, a blank page, the last step of an add), PDFium cannot be interrupted, and the only way to end it would be to end the engine, which loses every change of the document that is not saved. So there is no Stop button for such a change, Escape does nothing in its box, and a Stop that comes too late is answered with "this step cannot be stopped any more". A change to the document reports its progress after each page it has done, and at most four times a second (a turn, a crop, the clearing of form fields before a delete, the reading of the page tree, the writing of entries onto pages, the moves, the check of the pages after a move and the write-out that ends an insert all do; a single page being read, or one call of PDFium, says nothing while it runs), and every sign of life renews the wait of five minutes, so a healthy change to a long document of pages with a lot on them is not ended for being slow. The overall limit of a change is 20 minutes (plus the time the document would take to be read four times at one megabyte a second). An engine that says nothing for five minutes, or goes on past the limit, is ended, and the window says that the change took too long, not that the file may be damaged; the changes that were not saved are lost then, as they are for any lost engine. A single page that takes more than five minutes to read cannot report while it is read. While a change is under way the window is not held. The box that says what is being done (with its bar, and Stop where there is one) sits at the foot of the window, names the document, covers neither the tabs nor the buttons and takes no keys: the other tabs and the menu work, and Ctrl+S, Ctrl+P and Ctrl+W act on the document in front (undo, redo and the page tools wait in every document until the change has ended), so the other documents can be shown, saved, printed and closed as usual. Saving or printing the document that is being changed waits a moment and then says that the change is under way (or, while its pages are being copied out, which changes nothing in it, that they are being copied). Closing it, or quitting, waits a moment too and then asks: wait, or close (quit) now and lose the change under way and the unsaved changes of that document (the other documents are asked about as usual; while pages are being copied out the question says so, and it is the copy and the unsaved changes that are at stake). A second press of the close button brings that question up at once.
- *A second file that cannot be used.* When the file whose pages are added makes its engine crash, hang or fail to start, or does not allow its pages to be copied, the message names that file and the document is left open with its unsaved changes. With several files, the pages of the files before the one that failed stay and the message says so. That holds for everything that happens in the engine of the other file; in the last step the bytes of the file are read and copied by the engine of this document, and a file that made that step crash would close this tab like any damaged file (no such file was found).
- *Permissions of protected documents.* A document that forbids it (the permission bits of its security handler) cannot have pages inserted, deleted, moved or turned (assembling, bit 11 from revision 3, the modify bit before), cannot have the boxes of its pages changed (bit 4), and cannot have pages copied out or inserted from it into another file (bit 5). The window says which. Taking a change back is not checked, because no change could have been made.
- *What is not proved.* The pages' behaviour is tested on Linux, Windows and macOS in CI (the engine and client tests run on all three); the check with qpdf and poppler runs on Linux only. A real file dialog, a real network drive and the keyboard and pointer of a real web view were not tried: the browser tests run the real window code in Chromium against a stand-in for the app process. A move of a document with thousands of long pages was timed only on made-up documents.

## Signing with a certificate

A document that already holds signatures, an encrypted document and a document with an XFA form are not signed: a signature has to be added to the original bytes to keep the ones that are there, which Patient Partridge does not do yet, and a full rewrite by PDFium (which every save is) breaks them. The file is written once by PDFium and the signature is added after it, so a document whose structure the engine cannot read as a whole (a page list it cannot follow, a form it cannot parse) is refused with "cannot be signed", which says nothing about the document. A field that is kept apart from the box that shows it is refused too. The key stays in the signer process while a signature is made and is let go when the file is written, the box is closed or the app ends; the memory of the signer is overwritten where Patient Partridge controls it (the password, the messages that carry it), and not inside the libraries that open the file. No time stamp and no long-term checking data are written: a signature made today will show as "signer not verified" in this program and as the person's program decides in others, and nothing here makes it checkable after the certificate has expired. A name with letters outside the Western European set is kept whole in the signature and shown with a question mark in the box on the page. Only RSA with PKCS #1 v1.5 and ECDSA are signed; Ed25519, RSA-PSS and other curves are refused because other programs do not read them. The look is checked by drawing it with Poppler and by reading the file with qpdf, OpenSSL and a validator written by someone else; it was not tried in every program people use. Certificate files from the keychain or the certificate store of the system (no file) are not offered. After a file is signed here, the tab it opens in does not allow edits, but the page tools of the side panel are not held back by this: a change made with them is refused at the next save like any change to a signed file.

## Saving and digital signatures

**Protected documents with XMP metadata (since 0.2.2).** PDFium writes the XMP metadata stream of a document (title, author, keywords) without encryption, also when the document has a password and its metadata should be encrypted. A save of such a document is refused with a message instead of writing the metadata in the clear; saving a copy does not help. A protected document without XMP metadata, or one whose file says its metadata is to stay unencrypted, is saved as before, with every other stream encrypted.

A save always writes the whole document again. PDFium has an incremental save that appends the changes to the original bytes and so keeps a signature valid, but the Rust binding used here (pdfium-render, 0.9.5 and the newest, 0.9.6) always saves without it, and the document handle it would need is not public. So a save of a signed document breaks the signature: programs that check it will say the document was changed after it was signed. The app asks before it does that (Cancel, Save a copy, Save anyway). It cannot tell whether a signature allows the change; it warns for every signed document. The signature itself stays in the file. How signatures are shown and checked is described in [Digital signatures: what is checked](digital-signatures.md).

## A file that changes while it is open

If another program rewrites the file in place while it is open here, **every edit you made since you opened it is lost**: Save and Save a copy both refuse, and the only way forward is to close the tab and open the file again. There is no way yet to carry the edits over to the new version of the file. PDFium reads a document as it needs it, so the engine keeps the file open and reads the rest of it during a save. If another program rewrote the file in place (same file, new bytes) since the document was opened, what the engine would write is a mix of two versions. So the engine watches the file: it reads it in blocks of 32 KiB and keeps a digest of every block it has read, and before and after a save it checks that the size of its handle is what it was, that every block read so far still has its digest, and that no read failed. If not, nothing is serialised and both Save and Save a copy say that the file changed while it was open and that it has to be opened again (the changes made since cannot be saved, and are lost when the tab is closed). A new time of change alone, as when a program only touched the file, is not a change when every block of the file had been read before it moved. When some blocks had not been read yet, nothing seen differs but the rest cannot be compared with anything, so the file counts as touched: Save does not replace the original (it says so and offers a copy), Save a copy works and says in one line that the file was touched and that the copy holds what the app had read, and the original is never replaced. A change in a part of the file that was never read, with the size kept and the time of change put back, is not seen; nothing of the document depends on that part. A file that was replaced by a new file under the same name (the way most editors save) leaves the engine with the old file, whole: Save asks whether to replace the other version, and Save a copy writes the document that was opened.

## What the check of a saved file can and cannot catch

The new file is flushed, read back and compared with what was received, then opened by a second sandboxed engine. The read-back comes from the system's cache as a rule, because the bytes were written a moment ago, so it shows that what was written is what was sent; it cannot show that the disk stored it, and no program can prove that from outside. A fault of the media itself is not caught. The two engines must agree on the number of pages, the size of every page, that every page loads, the text of every page, the number of page objects and annotations on every page, the kind of protection and the number of signatures; a file with a password must still ask for it. Not caught: a change that leaves all of that as it was (a different colour, a moved image, the same words in another font), anything in a part of the file no page uses, and a fault in PDFium that damages the document before both engines read it in the same way. The check does not look at pixels.

## Quitting with unsaved changes

Closing the window and Alt+F4 ask first on all three systems. On macOS the standard menu's Quit (Cmd+Q) is replaced by an entry of the app's own that asks too; Windows and Linux have no menu bar, so they have no Quit entry. **Quitting from the Dock's menu, a log out, a restart and a shut down cannot be held back on macOS**: macOS ends the program through the system there, and Tauri does not let the app refuse. Unsaved changes are lost in those cases without a question. **On Windows and Linux** the app asks only when the window is closed, with the close button or Alt+F4. Nothing in the app handles the end of a session (a log out, a restart or a shut down), and it has not been tried on either system, so assume that unsaved changes are lost without a question there too. Save before you log out, restart or shut down. If a save that Save and quit started takes more than a moment, a box shows that it is going on and offers Cancel (the program stays open and the save carries on) and Quit without saving; a second press of the close button or Cmd+Q brings the box up at once, so neither is ever dead. Quitting without saving while a file is being written leaves the old file as it was, and may leave a stray `.name.pdf.partridge-*.tmp` next to it.

## Saving, size and the file system

A document is saved only if the saved file would be at most 512 MiB (the engine builds it in memory). A save needs room for a second copy of the file on the same disk. The engine is given as long as it keeps reporting progress, but not for ever: a save, and the look at the document that goes with it, have an overall limit of 10 minutes plus the time the file would take to be read four times at 1 MiB a second (about 45 minutes for a 512 MiB file). When it runs out the engine is stopped and the window says so; the file on the disk is not touched, and the changes made since the document was opened are lost.

Replacing a file keeps its permissions and, where it can, who may open it: on Linux and macOS the mode, the owner, the group and the access control list (the POSIX ACL on Linux, the extended ACL on macOS); on Windows the owner and the access rights (the DACL, with its protection from inheritance). All of it is given to the new file before anything is written to it. Where the owner, the group or the access rights cannot be given to the new file (making someone else the owner takes a privilege), the save stops before it writes anything and offers Save a copy; it does not change who owns or may open a file without saying so. What is not carried over, and not asked about: extended attributes such as macOS tags and the quarantine flag, and security labels such as SELinux contexts.

A file with more than one name (a hard link, on any system) is not saved in place, because the other names would keep the old file; a copy is offered. A symbolic link is followed and stays a link. The app tries to open the file for writing before it does anything else, so a file you may not write is refused even when its folder is writable. On a network drive the replacement is as safe as the drive makes it: the new file is written and flushed next to the old one and checked before the rename, so a lost connection leaves the old file. On Windows the engine keeps the file open for as long as the document is open, and FAT, exFAT and network drives cannot replace a file that is open: there the save says exactly that ("the file cannot be replaced here") and offers a copy. NTFS is not affected. "Changed by something else" is judged by size, time of change and, where the system has one, the file identity; the last check comes just before the rename and cannot close the gap of that moment.

A program that was killed in the middle of a save can leave a file named like `.name.pdf.partridge-123-456.tmp` next to the document; the next save of that document removes it once it is a day old. For a password-protected document the app keeps the password in memory while the document is open, to check the saved file; it is overwritten with zeros when the document is closed. It is not protected against a dump of the app's memory.

## Reloading the window

Reloading the window (F5, Ctrl+R, the context menu of the page) is switched off in release builds, because a reload would lose the tabs. The right mouse button on selected text opens a small menu of the app with Copy; text boxes keep the menu of the web view (Cut, Copy, Paste). There is no menu on the page itself, so there is no Paste or Select all by mouse outside the boxes. Whatever else restarts the page, the app ends the engines of the old page and starts clean.
