# Known limits

This page lists what Patient Partridge does not do yet, and where its edges are. The [README](../README.md) names the main ones; here they are in full. What the app does is in [features.md](features.md); how it is protected is in [security.md](security.md).

The rest of the editor (creating forms, signatures, editing text and images, redaction, page tools and the other steps on the roadmap) is planned and does not exist yet; see the [Roadmap](../README.md#roadmap).

## Annotations

- *Colour.* The engine draws a note the same way whatever its colour (PDFium has one picture for it), so a note has no colour to choose. The colour of a highlight, an underline or a strike-out can be changed in place: the picture of the annotation is made again and the colour entry is set, and every other entry of the annotation (rich text, name, dates, opacity, layer, popup, replies) stays as the file had it; the opacity is kept to within 1/255. Changing the colour replaces the picture with a plain one in the new colour, and Undo makes a plain picture in the old colour, not the file's own picture. The old colour is read from the first path of the picture that paints something (the fill of a highlight and the stroke of the others when they are painted, otherwise the other one), also when the picture draws through forms inside forms; a picture with no path to read it from is not recoloured (the bar says so).
- *Text.* The text of a file's annotation is edited only when it is shown whole: a comment longer than 4 KiB, or with characters the window does not show, can be read but not edited here. Line ends written as CR are shown as line feeds and written back as they were when a change of the text is taken back. Editing the text of an annotation that has rich text (`/RC`) replaces the rich text with the plain text, so its formatting is lost; taking the edit back (Undo) writes the comment, the rich text and the date of the last change as the file had them.
- *Undo and delete.* An annotation that a file already has cannot be put back by Undo after it is removed (a copy would lose what the engine does not read), so deleting one asks first; one made in this session can be put back. Deleting one from a file is not an entry in the history: Undo still takes back the changes made before it, and the document counts as changed until it is saved. Edits that were made to that same annotation before it was deleted do nothing when they are undone or done again, and Undo goes on to the edits below them.
- *What a delete leaves in the file.* Deleting an annotation and saving rewrites the whole file, and the text of the comment, its author, its rich text and its subject are not in the new file; its popup goes with it. If a reply or the document's tag structure refers to the annotation, an empty record of it stays, with its place on the page and its dates. **This is not redaction:** nothing on the page itself is removed, and copies and backups made before the save still hold the text. PDFium does not write the objects of a loaded file that nothing refers to any more (also when they sit in object streams), but it does write those made in the session, which is why the text of those is overwritten when they are removed or changed.
- *The exception.* A free text box that came without an appearance stream (the entry is optional) keeps its words in the new file after it is deleted. PDFium makes the appearance, with the words in it, when the page is first drawn, and writes it into the saved file although nothing refers to it any more, and no call of PDFium overwrites it. The question before a delete says so for text boxes.
- *Boxes and moves.* A note cannot be moved off its page. A box a file puts outside its page is cut to the page in the window; a note a file puts partly outside its page can be moved in and then moved back to where it was, and not further out.
- *Kinds.* A drawing is written with a list of strokes and an appearance stream; PDFium cannot move or change the strokes of an existing drawing, so a drawing cannot be edited here, only removed. Free text boxes, squares, circles and squiggly underlines of a file are shown and can be removed, not changed. Link and form-field annotations are not listed. A stamp is a drawn frame and word in a standard font, not an image; its wording is fixed.
- *Permissions and signatures.* A document opened with its owner password may be annotated whatever the file grants the user. A document with a digital signature gets the warning described under [Saving and digital signatures](#saving-and-digital-signatures), because saving rewrites the file.
- *Other readers.* Whether commercial PDF readers let a person edit a drawing's strokes was not tried; `qpdf` and Poppler read the files without complaint.

## Memory

Measured on Linux (WebKitGTK, software rendering) with a 500-page file open: the whole app, all its processes together, uses about 490 MB of memory (proportional share), of which about 325 MB is the web view and about 14 MB the engine. The goal of 150 MB is not met there. Windows and macOS have not been measured on real hardware; their web views behave differently.

## Web view

The look uses CSS `light-dark()`, so the web view must be recent: WebView2 (always up to date), WebKitGTK 2.46 or newer, and a macOS version whose web view is Safari 17.5 or newer.

## Search

Search finds text as PDFium reports it. It does not join words split by a hyphen at the end of a line, and it does not match a ligature character against its letters. A search stops after 20,000 matches and says so (for example "20,000+ (stopped at the limit)"); a page with more than 2,000 matches shows the first 2,000 and the find bar says that some pages have more.

## Text selection

Text selection follows the order of the text in the file. In documents with several columns that are stored in an odd order, a selection can jump between columns. Right-to-left text (Hebrew, Arabic) is selected from its right end, in reading order; text that runs sideways or up and down is not placed well yet.

The keyboard cannot select a stretch of text yet (Ctrl+A selects everything), and the pen needs a pointer: there is no way to draw with the keyboard.

## Text layer

For each document the window keeps the text of at most 1.5 million characters (about 60 MB) for the pages on screen, and the addresses of their links up to 1 million characters. A page that would go past that is drawn as usual but has no text layer for the moment: its text cannot be selected, searched on the page or pressed as a link, and a message says so once. The window also draws at most 20,000 boxes for the selection and the search matches together, and 5,000 link buttons, for a document, and keeps at most 120 pages on screen at once. A page that does not get all its boxes or buttons is drawn as usual and a message says so once; copying and searching are not affected. Normal reading does not reach these numbers. A very small zoom on a large screen can, with a search for a common letter or with index pages that hold hundreds of links each. The text limit itself is reached only by files made to do it, such as thousands of tiny pages that each hold the most text a page can have.

## Copying

Copying gathers at most 20 million characters at a time, one copy at a time for each document. When a copy is cut short, or a page cannot be read, or a page has more text than the engine hands over (100,000 characters), a message says what is missing. On some systems the web view allows the text to be put on the clipboard only straight after a key press; if it refuses, a message says so.

## Printing

Printing sends pictures of the pages, at 150 dpi, to the system's print dialog. Pages of different sizes are fitted to the paper. One print job holds at most 1,000 pages: for a longer document the dialog offers "The first 1000 of N pages" instead of "All", and a list of pages can be printed in parts. Printing has not been tried on a real printer on any system yet (see [features.md](features.md#printing)).

## Fonts that a PDF does not embed

The engine runs in a sandbox that does not let it open files, so it cannot look at the fonts installed on your system. For Latin text it uses the fonts built into PDFium (Helvetica, Times, Courier and anything named like them). For Chinese, Japanese, Korean, Arabic, Hebrew and Thai the app picks one font file for each script from a fixed list of the files that Windows, macOS and the usual Linux font packages install (the PDF never chooses a file), opens each read-only, and hands the engine those handles; the engine reads a font only when a page needs that script, checks it, and hands PDFium at most 512 MiB of font data for a document. [system-fonts.md](system-fonts.md) lists the files per system. Only those file names in the system's own font folders count: a font that is installed for one user only, or has another file name, does not, even if it covers the script. The list is read again each time a document is opened, so a font you install for all users is used from the next document you open (close the tab and open the file again: a tab that is already open keeps what it had); a file that is missing, cut short or not a font is passed over for the next one in the list. CI draws a page in each of the seven scripts with what the images of the GitHub runners have (Windows and macOS as they come, Ubuntu with the Noto and DejaVu font packages), and also as a standard Windows user. A collection file (.ttc) is used from its first face, and one file can serve several scripts (on macOS the same Chinese font serves Simplified and Traditional, on Windows Segoe UI serves Arabic and Hebrew). Chinese, Japanese and Korean are drawn from the character set the PDF asks for, whatever the font is called, also when the name is written in the code page of the language (GBK, Shift-JIS, EUC-KR, Big5). Arabic, Hebrew and Thai are drawn only when the PDF names a font made for that script (such as Traditional Arabic, David or Angsana), because PDFium asks for those by name alone: text in them that a PDF sets in Arial, Tahoma or Times New Roman without embedding the font shows as blanks, and the window does not know that it does. When the PDF needs a font for a script, the computer has none of the listed ones (or the document asks for more copies of fonts than the 512 MiB allow: PDFium keeps one copy for each combination of font name, weight and slant, and font objects that ask alike share it), that text shows as blanks and the window says so once for the document; you can still search, select and copy it. Almost every PDF made for print or the web embeds its fonts and is not affected. Fonts put in a `fonts` folder next to the PDFium library are read at start and used too; the app does not ship any.

## Forms

XFA forms (the kind drawn from XML data, whole or next to ordinary fields) are shown but not filled in: a reader that supports XFA would show the XFA data and ignore ordinary fields, so a value written to them would not appear. The app says so in a bar over the pages. PDF JavaScript never runs, so a form that adds up, checks or formats values by script opens and can be filled in, but those fields do not update; the app says so once, in the same bar, when it finds a script or an action on a field (it looks at the scripts of the document, the words of the file, and the actions on the fields of the pages it shows, so a script hidden in a compressed part of a document it does not otherwise meet can go unnoticed).

**Actions that change a form are checked before you can fill it in, and the check has a limit.** PDFium runs the actions of a field that are not scripts by itself when the field gets the focus, is pressed or is left, and two of them change the document: a reset of the form and a hide of fields. So the app reads the actions of a form before it lets you fill it in: the engine writes the document out once and, if it holds a reset or a hide, reads what the actions of every dictionary do: it follows `/A` and `/AA`, through references and `/Next` (one action or an array of them), to see whether a chain reaches a reset or a hide. A field is left read only and marked in two cases. If its own actions reach one, that field is left alone, and nothing else is: a reset button, a script that formats a date or a number, or a link next to it do not stop other fields. If the keystroke, validate, format or calculate event of any dictionary reaches one, every field of the form is left alone, because PDFium reads those events from a field other than the widget (it looks up `/Parent`, builds a field from the list of its kids, and joins two dictionaries with one full name by that name alone), and the file does not say which widget belongs to which. Every field is also left alone when the search cannot settle: an action that points to nothing, a loop, a chain or nesting that is too long, more work than the limits allow, a file that failed to read or changed while it was searched, or a compressed object stream, whose content is not read. A widget with an action is matched with the dictionaries of the file by which of `/A` and `/AA` it has and by its box, not by its page or its place in a list; it is left alone when a dictionary with that box and those keys reaches a reset or a hide, and also when no dictionary matches, so a harmless widget with the box of a harmful one is left alone too. A dictionary with no `/Rect` at all (a page, the document, a bookmark, a field above its widgets) is not a widget and blocks no field, because PDFium never runs its actions from here. The bar says in plain words which of the two it is, says it again when the reader tries such a field, and a request to change it is refused.

**This is a reading of the file, not a guarantee:** a file built to get round it could still clear or hide a field in the open document. Nothing leaves the app, and the file on disk changes only if you save. Scripts never run, so a script that does not reach a reset or a hide through `/Next` blocks nothing. The other actions (a link, a jump, a launch, a submit, a named action) end in something the engine does not provide, so they do nothing. A push button over a field is never pressed: the field that is named gets the key, not whatever lies at its place. Push buttons and signature fields are not listed.

**Two kinds of choice cannot be taken back:** PDFium has no way to turn a radio button off, or to clear a drop-down list, once a choice is made, so the undo of the first choice in such a field is refused with a message (a different choice can be made, and undone). A field whose value is longer than 8 KiB, or a list with more than 500 choices, is shown and left alone. The Tab order is the order of the fields on the page (the order of the file); the page setting that asks for another order is not used. A field that is itself turned in its own right (the entry `/MK /R`), and not only by the page, is drawn turned by PDFium but its control is not. Text that a field's font cannot draw (a script the fonts of the engine do not cover) is stored correctly but the picture of the field may show blanks, until a reader that has such a font redraws it.

Which readers were tried: poppler, qpdf and pdftk read the saved test files in CI; commercial PDF readers have not been tried by the project.

## Saving and digital signatures

A save always writes the whole document again. PDFium has an incremental save that appends the changes to the original bytes and so keeps a signature valid, but the Rust binding used here (pdfium-render, 0.9.5 and the newest, 0.9.6) always saves without it, and the document handle it would need is not public. So a save of a signed document breaks the signature: programs that check it will say the document was changed after it was signed. The app asks before it does that (Cancel, Save a copy, Save anyway). It cannot tell whether a signature allows the change; it warns for every signed document. The signature itself stays in the file. Validating signatures is not there yet.

## A file that changes while it is open

If another program rewrites the file in place while it is open here, **every edit you made since you opened it is lost**: Save and Save a copy both refuse, and the only way forward is to close the tab and open the file again. There is no way yet to carry the edits over to the new version of the file. PDFium reads a document as it needs it, so the engine keeps the file open and reads the rest of it during a save. If another program rewrote the file in place (same file, new bytes) since the document was opened, what the engine would write is a mix of two versions. So the engine watches the file: it reads it in blocks of 32 KiB and keeps a digest of every block it has read, and before and after a save it checks that the size of its handle is what it was, that every block read so far still has its digest, and that no read failed. If not, nothing is serialised and both Save and Save a copy say that the file changed while it was open and that it has to be opened again (the changes made since cannot be saved, and are lost when the tab is closed). A new time of change alone, as when a program only touched the file, is not a change when every block of the file had been read before it moved. When some blocks had not been read yet, nothing seen differs but the rest cannot be compared with anything, so the file counts as touched: Save does not replace the original (it says so and offers a copy), Save a copy works and says in one line that the file was touched and that the copy holds what the app had read, and the original is never replaced. A change in a part of the file that was never read, with the size kept and the time of change put back, is not seen; nothing of the document depends on that part. A file that was replaced by a new file under the same name (the way most editors save) leaves the engine with the old file, whole: Save asks whether to replace the other version, and Save a copy writes the document that was opened.

## What the check of a saved file can and cannot catch

The new file is flushed, read back and compared with what was received, then opened by a second sandboxed engine. The read-back comes from the system's cache as a rule, because the bytes were written a moment ago, so it shows that what was written is what was sent; it cannot show that the disk stored it, and no program can prove that from outside. A fault of the media itself is not caught. The two engines must agree on the number of pages, the size of every page, that every page loads, the text of every page, the number of page objects and annotations on every page, the kind of protection and the number of signatures; a file with a password must still ask for it. Not caught: a change that leaves all of that as it was (a different colour, a moved image, the same words in another font), anything in a part of the file no page uses, and a fault in PDFium that damages the document before both engines read it in the same way. The check does not look at pixels.

## Quitting with unsaved changes

Closing the window and Alt+F4 ask first on all three systems. On macOS the standard menu's Quit (Cmd+Q) is replaced by an entry of the app's own that asks too; Windows and Linux have no menu bar, so they have no Quit entry. **Quitting from the Dock's menu, a log out, a restart and a shut down cannot be held back on macOS**: macOS ends the program through the system there, and Tauri does not let the app refuse. Unsaved changes are lost in those cases without a question. **On Windows and Linux** the app asks only when the window is closed, with the close button or Alt+F4. Nothing in the app handles the end of a session (a log out, a restart or a shut down), and it has not been tried on either system, so assume that unsaved changes are lost without a question there too. Save before you log out, restart or shut down. If a save that Save and quit started takes more than a moment, a box shows that it is going on and offers Cancel (the program stays open and the save carries on) and Quit without saving; a second press of the close button or Cmd+Q brings the box up at once, so neither is ever dead. Quitting without saving while a file is being written leaves the old file as it was, and may leave a stray `.name.pdf.partridge-*.tmp` next to it.

## Saving, size and the file system

A document is saved only if the saved file would be at most 512 MiB (the engine builds it in memory). A save needs room for a second copy of the file on the same disk. The engine is given as long as it keeps reporting progress, but not for ever: a save, and the look at the document that goes with it, have an overall limit of 10 minutes plus the time the file would take to be read four times at 1 MiB a second (about 45 minutes for a 512 MiB file). When it runs out the engine is stopped and the window says so; the file on the disk is not touched, and the changes made since the document was opened are lost.

Replacing a file keeps its permissions and, where it can, who may open it: on Linux and macOS the mode, the owner, the group and the access control list (the POSIX ACL on Linux, the extended ACL on macOS); on Windows the owner and the access rights (the DACL, with its protection from inheritance). All of it is given to the new file before anything is written to it. Where the owner, the group or the access rights cannot be given to the new file (making someone else the owner takes a privilege), the save stops before it writes anything and offers Save a copy; it does not change who owns or may open a file without saying so. What is not carried over, and not asked about: extended attributes such as macOS tags and the quarantine flag, and security labels such as SELinux contexts.

A file with more than one name (a hard link, on any system) is not saved in place, because the other names would keep the old file; a copy is offered. A symbolic link is followed and stays a link. The app tries to open the file for writing before it does anything else, so a file you may not write is refused even when its folder is writable. On a network drive the replacement is as safe as the drive makes it: the new file is written and flushed next to the old one and checked before the rename, so a lost connection leaves the old file. On Windows the engine keeps the file open for as long as the document is open, and FAT, exFAT and network drives cannot replace a file that is open: there the save says exactly that ("the file cannot be replaced here") and offers a copy. NTFS is not affected. "Changed by something else" is judged by size, time of change and, where the system has one, the file identity; the last check comes just before the rename and cannot close the gap of that moment.

A program that was killed in the middle of a save can leave a file named like `.name.pdf.partridge-123-456.tmp` next to the document; the next save of that document removes it once it is a day old. For a password-protected document the app keeps the password in memory while the document is open, to check the saved file; it is overwritten with zeros when the document is closed. It is not protected against a dump of the app's memory.

## Reloading the window

Reloading the window (F5, Ctrl+R, the context menu of the page) is switched off in release builds, because a reload would lose the tabs. The right mouse button on selected text opens a small menu of the app with Copy; text boxes keep the menu of the web view (Cut, Copy, Paste). There is no menu on the page itself, so there is no Paste or Select all by mouse outside the boxes. Whatever else restarts the page, the app ends the engines of the old page and starts clean.
