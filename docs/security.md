# Security: what is protected and what is not

Please read this before you open files from people you do not trust.

The short version is in the [README](../README.md#security). This page is the full text. For how the app and the engine are put together, see [architecture.md](architecture.md); for the limits of the features, see [known-limits.md](known-limits.md).

## What the sandbox does

PDFium is the main attack surface: a large C++ library that parses files nobody has checked. Every open document has an engine process of its own, and that process locks itself into an operating system sandbox before it reads the first byte of the document. If an attacker finds a bug in PDFium and builds a PDF that exploits it, the code runs inside that sandbox:

- **It cannot open files.** The engine does not open files at all. The app opens the document and hands the engine a read-only handle to that one file when it starts the engine. The engine can read that file, and the few system font files described in [system-fonts.md](system-fonts.md), and nothing else, cannot write or create files, and cannot see the other open documents (each has its own engine). One limit: on Windows the protection comes from file permissions, and FAT and exFAT volumes (many USB sticks and SD cards) have none, so a program in the engine could read, write and delete files there if it knew the path. NTFS and the file systems of macOS and Linux are protected. On Linux the system call filter cannot read a path, so where the system does not allow the extra layer below (an empty root file system, which needs user namespaces) the engine can still ask whether a path exists and how big it is, but not read it.
- **It cannot use the network, start programs or touch other processes.** The engine's code contains no network code apart from the few attempts its own sandbox check makes on purpose, which must fail (a check in CI keeps the rest of it free of network code), and the sandbox stops the operating system from letting any code in the process reach the network. On Linux and macOS it refuses to make a socket. On Windows the engine runs in an AppContainer without the capabilities that allow a network, with a token that holds no privilege, so Windows refuses a TCP connection, the making of a socket of any kind that was tried (datagram, raw ICMP over IPv4 and IPv6, and the Unix, Hyper-V and Bluetooth families) and a name lookup, loopback included. What is known about how, and what is not, is under "What it does not cover" below.
- **It cannot use more than 3 GiB of memory, by different means.** Windows: the job object, in the kernel. Linux: a data limit, and the filter refuses shared, grow-down and executable memory, which the limit would not count. macOS: the system does not enforce limits on memory, so the app watches the engine from outside and ends it above 3 GiB; the engine has a watch of its own as a first line, but code that has taken the engine over can stop that one, and the app's cannot be stopped from inside. This is a watch, not a wall: it looks about every 25 milliseconds (longer when the computer is busy), so what it promises is that an engine that stays above 3 GiB is ended within a fraction of a second, and what it does not promise is anything about memory used for less time than that. An engine can go past the limit by what it manages to take between two looks (a few hundred megabytes on current hardware), and one that takes memory and lets go of it again, or ends, within one look is never ended, though it also leaves nothing behind. The limit counts the memory footprint of the engine, the figure the system uses to choose which process to end when memory is short (compressed memory counts), not address space. A test in CI starts a program that takes three times the limit and keeps it, with the engine's own watch switched off, and requires that the app ends it from outside.
- **It knows nothing of the app's environment.** The engine is started with an empty environment (on Windows only the system folder), so tokens and keys in the shell the app was started from do not reach it.
- **How, per system.** Linux: a seccomp filter that allows only the few system calls the engine needs (always applied; nothing that opens files, creates sockets, starts processes, traces other processes, sends signals or makes memory executable or shared), plus Landlock where the kernel has it (5.13 or newer; it is applied before the engine starts any thread of its own, because Landlock holds only for the thread that applies it and the threads started after, and the engine names it in its greeting only when it holds for every thread), plus an empty root file system (a user and a mount namespace) where the system allows it; the engine tells the app which of these ran. macOS: a Seatbelt profile that denies everything by default, the mechanism browsers use for their renderers. Windows: an AppContainer without capabilities (the mechanism of Windows apps and of browser sandboxes; the system blocks all network use of such a process) made from a restricted token with no privileges (not even the right to skip the check of folders on the way to a file, which Windows keeps by default and which the app removes) and no accessible group, the untrusted integrity level, a job object of its own (one process, a memory limit, no child processes, no clipboard, no user interface access), a desktop of its own (the engine cannot see the windows of the user, read the screen or draw over their windows; if Windows refuses to create the desktop, the engine is started on your desktop instead, does not report this layer, and the app neither tells you nor stops it; whether the engine can start there at all has not been tried), process mitigation policies (no dynamic code, no extension points, strict handle checks and others), and an explicit list of the handles the engine inherits: its three standard streams and the document, and, when the system's fonts are passed on for scripts the bundled ones lack, one read-only handle for each font file (at most seven), so up to eleven in all.
- **It checks itself.** After the sandbox is applied the engine tries to open a file and must be refused; it also tries to use the network (Linux and macOS: making or using a socket, which must be refused; Windows: a TCP connection and a UDP datagram to the loopback address, and a raw ICMP socket over IPv4 and over IPv6, all of which must fail with "access denied"). It also checks that the token is restricted, holds no privilege and is an AppContainer token. The greeting names only the layers that were checked. A release build that cannot show a working sandbox does not open the document and tells you so. On Windows the network answer is the one check that is not required for opening: the AppContainer token and every other layer are, but if the system answers a network attempt in another way, the engine still opens the document, says in its greeting that it could not prove the network block (`network-not-proved`, with what the system answered), and the window shows one line about it. Nothing is then claimed that was not shown. No computer or test state has produced that answer so far; the path is tried in CI with a debug engine that is told to treat the answer as unproved. The app also refuses an engine that does not report a sandbox. A debug build, used for development only, may go on without one.

## What it does not cover

- **On Windows, what blocks the network, what is known and what is only inferred.** Known, from tests in CI that run from inside the sandboxed engine and are repeated in a copy of the program outside it: a TCP connection to a listener, to a computer on the Internet, over IPv6 and to an address of the computer that is not the loopback one fails; a datagram socket, a raw ICMP socket (IPv4 and IPv6), and sockets of the Unix, Hyper-V and Bluetooth families cannot be made (`socket` fails with "access denied"); a path on another computer, a named pipe that is open to everybody and a name lookup fail; and the engine cannot open the device that every socket is made from (`\Device\Afd\Endpoint`, "access denied"), which it could if the token still held the privilege that lets a program skip the check of folders on the way to an object. All of this was seen in the default state of the firewall on Windows Server 2025 and 2022, as the administrator of the runner and as a standard user, and with the firewall profiles switched off on both server images, as the administrator. With the default for outgoing traffic set to allow, with a rule that lets the engine's package out and with a loopback exemption for the package, it was tried on Windows Server 2025 only, as the administrator. Known, from an earlier version of the code that kept that privilege: a raw ICMP socket could then be made in the AppContainer, and an echo request be sent from it; the same was true with the less privileged kind of AppContainer. A packet capture (`pktmon`, job "Windows, packet capture") on both server images showed that the five echo requests sent that way to an address nobody answers were dropped inside the network stack with the reason "Inspection drop" and never reached the network card, while the same requests from a program that is not sandboxed did; that is one place and one address, and it does not say which filter dropped them. Inferred, from reading Microsoft's network driver and not tested: the first refusal of a TCP or datagram socket is an access check of the driver on the endpoint, against a fixed list that has no entry for a token with no network capability, and not the filtering platform (the part of Windows that also runs its firewall); and a raw ICMP socket is open to every token by the design of Windows, which is why only the device closes it. Not known: whether the refusals depend on the filtering service running (the runners of GitHub do not let anyone stop the firewall service or the filtering engine, so that state and third-party firewall products have not been tried), which filter dropped the echo in the capture below (the capture shows where the packet stopped, not why), and what Windows 10 and Windows 11 themselves do (not in CI; see `docs/windows-sandbox.md`). The name lookup fails with "no recovery", not with "access denied", so that one shows that the lookup does not work, not why.
- **On Windows the app, and the installers, add an entry for the engine's package to the access list of the engine's own files.** The AppContainer can open only what is open to its own package or to "all application packages". The folders of Windows and Program Files are open to the latter. A per-user install (in `%LOCALAPPDATA%`) is not, so the app adds a read-and-execute entry for the engine's package to the engine program, the PDFium library and the folders they are in. The package is a number computed from a fixed name; no profile is created. The user owns those files, so no administrator rights are needed. The MSI and the NSIS installer add an entry for that same package, and for nothing else, when an administrator installs in a folder outside Program Files (where the user cannot add it): read and execute on the install folder, without inheritance, and on `partridge-engine.exe` and `pdfium.dll` by name. No other application package gains anything, and a file of yours in the same folder gets no entry, so installing in `Documents` or at the root of a drive opens nothing there. The installers remove the entry on the folder when the program is uninstalled; the entries on the two files go with the files. The MSI also writes one marker value under `HKLM\Software\Patient Partridge Installer`, which it removes again on uninstall. An entry the app adds itself stays when the app is closed or removed, and an update that replaces a file loses it and the app adds it again at the next start. The package can read and run those files; it cannot write them, and the restricted token (its only restricting SID is one that no object grants) still makes the engine unable to open them after it has locked itself in.
- **Version 0.2.x, released so far, has no AppContainer.** The engine on Windows is only under a restricted token, which does not stop it from using the network: a test in CI found that such a process can still make a socket and connect. An exploited engine of 0.2.x could send out what it can read, and it can clear the clipboard, though not read it or put anything on it. The AppContainer described above is new in 0.3.
- **The app writes the saved files, and the bytes it writes come from the engine.** They are untrusted: the size and every piece are checked against the caps, and a new sandboxed engine has to open the written file before it replaces the old one. That check shows that the file opens and is the same document in page count, protection, signatures and a fingerprint of every page (its size, text and number of objects and annotations); it does not show that every page looks the same, and it does not look at pixels.
- **The app itself is not sandboxed.** The window, the web view and the code that starts the engines run with your user rights. The sandbox protects you from a bad PDF, not from a bug in the app.
- **The engine can still read the document it was given** and send back whatever it likes. The handle also tells a program that can ask which file it is on some systems (Windows for sure): the folder the document is in, and so the user's name. The app treats every answer from the engine as untrusted (sizes are checked, frames are limited, text only reaches the window as text), but a bug in that handling would be reachable from a hostile PDF.
- **A bug in the operating system kernel** can be used to leave a sandbox. This is true of every sandbox. On Windows the win32k system calls (a large part of that surface) are not switched off for the engine, because PDFium's DLL does not load without them; on Linux the system call list is short.
- **Weaker spots by system.** Windows uses an AppContainer, not the stricter "less privileged" kind, and its network block is the system's own, without a firewall rule. macOS uses the `sandbox_init` call, which Apple has marked deprecated but still uses itself and which browsers rely on; it is not the App Sandbox. On Linux without Landlock only the seccomp filter protects, and it does that completely for opening files, but not against a kernel bug.
- **CPU time and speed side channels** are not limited beyond the 60 second answer timeout, and attacks such as Spectre are not mitigated by the sandbox.
- **The sandbox starts after PDFium and the fonts are loaded**, and loading is not protected. Both come from the app's own folder, and PDFium is checked against a pinned checksum.
- **Documents the engine opens are untrusted by design; PDFium itself is not tested for correctness.** The sandbox limits the harm of a PDFium bug. It does not fix it.
- PDFium is pinned to one release and updated by hand ([steps](pdfium-updates.md)); a workflow that runs twice a week keeps one issue open while a newer release exists, and CI checks that the library that ships has no JavaScript engine (V8).

Other protections: the engine ends when the app ends (even when stuck inside PDFium), and PDFium is loaded only from the app's own folder after a checksum check at build time.

## Network use and PDF scripts

The engine code has no network code, apart from the few attempts its own sandbox check makes on purpose (they must fail), and a check in CI keeps it that way. The window loads nothing from the internet (strict content security policy). **The only network use of the app is the update:** it checks GitHub for a newer version when it starts and every 6 hours, and downloads one only when you press Download and Install. The check can be turned off in the settings menu, and documents are never sent anywhere (see [updates.md](updates.md) for exactly what is sent). The one other thing that leaves the app is a link in a PDF that you say yes to: your normal browser is then started with that address, and a link goes nowhere unless you say yes.

PDF JavaScript is turned off. The PDFium build used has no JavaScript engine at all, and the form environment is made without a JavaScript platform. What that does and does not stop is described under [Forms in the known limits](known-limits.md#forms) and in [architecture.md](architecture.md).
